Autonomous Crazyflie Gate Racing

A vision-based autonomy stack for a simulated Crazyflie quadrotor: gate detection with OpenCV, geometric position estimation, 8-state FSM navigation, spatial memory, and cascaded PID control. EPFL MICRO-502 Aerial Robotics.

Simulation

Webots · Individual task · MICRO-502

Overview

A complete gate-racing autonomy stack built from scratch: perception, estimation, state-machine navigation, spatial memory, and cascaded PID control, for a simulated Crazyflie competing across three laps in a randomized 8x8 m arena with five unknown gates.

The Task

The arena contains five square gates arranged roughly in a circle around [4, 4]. Gate positions, sizes, and heights are randomized each run. The drone must complete three laps counter-clockwise within a 240 s cutoff.

01
Mapping lap -- gate positions are entirely unknown at takeoff. The drone must detect each gate from vision, estimate its world position, and fly through all five counter-clockwise. The clock does not run during this lap.
02
Timed laps 2 and 3 -- replay the remembered gate centers at maximum speed without needing vision. Evaluated on three randomized environments.
Computer Vision

Each gate has a magenta 0.4 m patch at center height as the primary visual cue. The pipeline converts the camera frame to HSV, thresholds for the magenta range, cleans the mask with morphological operations, extracts contours, and filters candidates by area, aspect ratio, boundary margin, and pixel density. Each candidate is scored by size, center bias, and magenta density; the highest score becomes the detection output, with angular offsets angle_x / angle_y derived from the 1.5 rad camera FOV.

Robust Confirmation

A single detection is noisy. Recent estimates are buffered and the median XY and Z across the window becomes the stable gate estimate. Candidates are rejected if XY or Z spread is too large, if the gate falls outside the expected angular sector for the current gate index, or if it is geometrically implausible relative to the arena. When a detection is promising but not yet confirmed, the drone enters a cautious probe approach to get a better view before committing.

Path Planning and Navigation

Gate Position Estimation

Converting a pixel detection to a world position requires drone pose and depth. The primary depth source is the range_front sensor; when it reads the wall behind the gate, a fallback uses the known 0.4 m patch height and camera FOV to compute image-based depth. Gate XY is projected from drone position along the composite bearing (yaw + angle_x), with Z from the vertical angle offset. All estimates are clipped to valid arena and height bounds.

8-State FSM

A finite-state machine drives top-level behavior. Transitions depend on detection confidence, timers, arena geometry, and simulator gate-credit callbacks. Arena geometry priors (five gates at radius 3.0 m around [4, 4], counter-clockwise) guide search direction, validate detections, and provide fallback estimates when vision is lost. If Search stalls, the controller replays the previous gate to reposition before retrying.

Gate Memory and Replay

After each successful pass, the controller fuses the confirmed median estimate, close-range visual candidates, and observed pass-path midpoints into a gate memory point. Gates that are never reliably detected receive a fallback from arena geometry priors. For laps 2 and 3, each gate is replayed in three phases: approach point, gate-center dwell, and exit point. Setpoint jumps are step-size limited so the PID never demands extreme tilt. Missed gate credits trigger retries with small lateral and vertical offsets.

Control

A [x, y, z, yaw] setpoint is converted to four motor PWM commands through four cascaded PID loops. Quaternion rotation projects inertial velocity into the body frame between the position and velocity stages.

01
Position PID -- XY and Z error to inertial-frame velocity setpoints.
02
Velocity PID -- body-frame velocity error to acceleration commands.
03
Attitude PID -- desired acceleration and yaw to roll, pitch, and yaw-rate setpoints. Acceleration clipped to ±π/6 rad.
04
Rate PID -- angular rate errors to motor mixing commands. Thrust computed from 3D acceleration with gravity compensation.

Challenges
  • Randomized layout -- no two runs are the same; the controller cannot rely on a fixed gate map
  • First-lap blindness -- gate positions are entirely unknown at takeoff; vision is the only source of truth
  • False positives -- arena walls and floor patterns produce magenta-like regions that must be rejected without discarding real gates
  • Oblique views -- approaching a gate from a bad angle shows a thin sliver of patch; the controller detects this and repositions perpendicular before attempting a pass
  • Range sensor wall bleed -- range_front sometimes reads the wall behind the gate; the image-depth fallback avoids this but adds uncertainty
  • Speed vs. reliability -- aggressive replay waypoints improve lap time but risk altitude loss or missed gate credits; step-size limiting and retry logic balance both

Simulation Outcome

The controller completes the full pipeline: take off, detect and estimate five unknown gate positions from vision, fly through each counter-clockwise, return to start, then execute two faster memory-replay laps. It handles vision loss, false positives, oblique views, range-sensor failures, and missed gate credits through fallback logic at every layer.
