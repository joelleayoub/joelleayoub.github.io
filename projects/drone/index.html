Autonomous Crazyflie Gate Racing in Webots

A vision-based autonomous flight controller that detects unknown gates with OpenCV, builds a spatial memory of their positions, and replays optimized gate-passing trajectories — all in the Webots simulator. EPFL MICRO-502 Aerial Robotics.

Overview

A complete gate-racing autonomy stack: perception, estimation, state-machine navigation, memory, and cascaded PID control — implemented from scratch for a simulated Crazyflie quadrotor competing across three laps in a randomized arena.

Problem Statement

The arena is an 8×8 m space containing five square gates arranged roughly in a circle around [4, 4]. Gate positions, sizes, and heights are randomized each run. The takeoff pad is fixed at [1, 4].

Three-phase race

01
Take off from the fixed pad at [1, 4, 0.1] and climb to search altitude.
02
Mapping lap — gate positions are unknown. Detect each gate using the onboard camera, estimate its world position, and fly through all five counter-clockwise. The clock does not run during this lap.
03
Timed laps 2 and 3 — replay the remembered gate centers at maximum speed without needing vision. The clock runs from leaving the start region to re-entering it.

Output at each timestep: a high-level setpoint [x, y, z, yaw] passed to a cascaded PID controller, which outputs four motor PWM values. Evaluation on three randomized environments with a 240 s real-time cutoff.

Computer Vision Pipeline

Each gate has a magenta 0.4 m patch at center height — the primary visual cue. The wooden frame is too easily confused with arena walls and fixtures.

Detection steps

01
Convert BGRA camera image to HSV.
02
HSV threshold isolates the magenta range.
03
Morphological open + close removes noise and fills gaps in the mask.
04
Contour extraction on the cleaned binary mask.
05
Filter by area, bounding-box size, aspect ratio, image-boundary margin, and magenta-pixel count.
06
Score each candidate by area, center bias, and magenta density. Highest score wins.
07
Output: bounding box, centroid, area, score, image size, and angular offsets angle_x / angle_y derived from the 1.5 rad camera FOV.
Gate Position Estimation

A single pixel detection is not a world position. Converting image-space to 3D requires the drone pose and a depth estimate.

Depth sources

Primary: range_front sensor, valid when the gate is squarely ahead. Fallback: image-based depth from the known 0.4 m magenta patch height and camera focal length derived from FOV — used when the range sensor reads the wall behind the gate instead of the gate itself.

Position projection

Given depth d, drone yaw ψ, and horizontal image angle angle_x:

Gate XY is projected forward from the drone position using the composite bearing ψ + angle_x. Gate Z is estimated from drone altitude plus the vertical projection through angle_y. All estimates are clipped to valid arena bounds [0.5, 7.5] and gate-height ranges [0.75, 2.1] m.

Robust Detection Confirmation

A single noisy detection can produce a wildly wrong world estimate. The confirmation layer requires temporal consistency before committing to a gate position.

Multi-detection median filter

Recent estimates are buffered. The median XY and Z over the window becomes the stable gate estimate. A candidate is rejected if any of these conditions fail:

  • XY spread across the buffer exceeds threshold — estimate is jumping around
  • Z spread is too large — altitude estimate is unstable
  • Estimated gate falls outside expected angular sector for the current gate index
  • Estimated gate is outside the plausible arena radius from [4, 4]
  • Bounding box is too small to be a reliable gate view
  • Gate direction is inconsistent with the expected counter-clockwise sector

Probe approach mode

When a detection looks promising but is not yet fully confirmed, the drone enters a cautious "probe approach" — moving toward the estimate to get a better view before committing. Special handling prevents accepting oblique side-views of the gate frame as a pass target for gates 3 and 4, which are often approached from difficult angles.

State Machine

The top-level controller is a finite-state machine with eight states. Transitions are driven by detection confidence, timer conditions, arena geometry, and simulator gate-credit callbacks.

Takeoff
Climb to 1.05 m, stabilize, then enter Search
Search
Yaw oscillation + altitude variation around expected gate sector
Scan Next
Brief scan after passing a gate before committing to Search for the next
Align
Visual servo to center gate in camera; set approach yaw and z
Approach
Move toward gate, refine estimate, collect memory candidates
Pass
Fly through gate along stored pass yaw; wait for simulator credit
Return Start
Navigate back to takeoff region to end mapping lap
Fast Laps
Replay remembered gate centers at speed — no vision needed

Arena geometry priors

The controller bakes in knowledge of the arena structure: five gates arranged around center [4, 4] at a search radius of 3.0 m, in counter-clockwise order. Each gate has an expected angular sector. This guides search direction, validates detections, and provides fallback estimates when vision is lost.

Recovery logic

If the drone gets stuck during Search (no confirmed detection after a budget expires), it can replay the previous gate to reposition itself before retrying the current gate. Boundary proximity triggers a retreat to the recovery radius before resuming search.

Visual Servoing and Approach

Servoing setpoints

Yaw: proportional correction from angle_x — positive detection offset steers the drone to face the gate. Altitude: Z command is updated from angle_y with an exponential smoothing blend toward the confirmed gate estimate.

Pass commit conditions

The drone commits to a pass through the gate when the detection is sufficiently centered (small angle_x) and the bounding box is large enough to indicate proximity. A timeout condition also triggers commit to avoid getting stuck. For thin side-on gate views, the controller stages in front of the gate — moving to a perpendicular position before attempting to fly through — rather than diving through from a bad angle and missing the gate volume.

Continuous refinement

During approach, the drone keeps updating pass_yaw and pass_z from fresh visual servo commands and stores memory candidates at close range, where estimates are most accurate.

Gate Memory and Fast Replay Laps

Memory construction

After each successful pass, the controller fuses several sources into a gate memory point:

  • Confirmed multi-detection median estimate
  • Visual memory candidates collected at close range during approach
  • Observed pass-path midpoints
  • Probe sightings from earlier in the approach

Each candidate is validated against angular sector, arena-radius bounds, boundary margins, and height limits before being accepted. Gates that are never reliably detected receive a fallback estimate from arena geometry priors.

Replay planner

For laps 2 and 3, each gate is replayed in three phases using the remembered gate center and the stored pass normal:

→
Approach point: a position 1.2–1.5 m before the gate along the pass direction.
→
Gate center dwell: fly to the remembered center at the stored height.
→
Exit point: a position past the gate to confirm the pass and set up for the next.

Setpoint jumps in XY and Z are step-size limited so the PID controller never demands extreme tilt or loses altitude authority. If the simulator does not credit a pass, the planner retries with small lateral and vertical offsets.

Cascaded PID Control

The low-level controller converts a [x, y, z, yaw] setpoint into four motor PWM commands through four cascaded loops.

01
Position PID — XY and Z position error → inertial-frame velocity setpoints. Quaternion rotation projects velocity into the body frame.
02
Velocity PID — body-frame velocity error → body-frame acceleration commands.
03
Attitude PID — desired acceleration + yaw → roll, pitch, and yaw-rate setpoints. Acceleration is clipped to ±π/6 rad before the attitude loop.
04
Rate PID — roll/pitch/yaw-rate errors → motor mixing commands. Combined thrust magnitude computed from the 3D acceleration vector including gravity compensation.

Output limits

  • XY velocity capped at 2.0 m/s
  • Z velocity capped at 0.75 m/s
  • Roll/pitch acceleration limited to ±π/6 rad
  • Motor PWM clipped to 0–600

The Z velocity cap was critical: large replay waypoint jumps could otherwise cause the drone to over-tilt and lose altitude authority, especially at higher speeds between gates.

Challenges
  • Randomized gate locations, sizes, and heights — no environment is the same; the controller can't be hand-tuned to a fixed layout
  • No gate map in the first lap — the drone must locate and estimate each gate purely from vision before it can be passed
  • False positives — arena walls, floor patterns, and lighting produce magenta-like regions that must be filtered without discarding real gate detections
  • Oblique views — approaching a gate from an angle shows a thin sliver of the patch; the controller must detect this case and reposition perpendicular rather than attempting a bad-angle pass
  • Range sensor wall bleed — range_front sometimes reads the wall behind the gate; the fallback image-depth estimator avoids this but adds uncertainty
  • Simulator gate credit tolerance — the drone must fly precisely enough through the gate volume; near-miss trajectories are not credited, requiring retry logic
  • Speed vs. reliability tradeoff — aggressive replay waypoints improve lap time but risk altitude loss or missed credits; step-size limiting and a retry mechanism balance both
  • Vision loss recovery — the drone can lose sight of a gate at any point; fallback memory, probe sightings, and forced-progress timeouts prevent getting permanently stuck

Outcome

The finished controller completes the full pipeline end-to-end: take off, search five unknown gates with vision, detect and estimate their world positions, fly through each counter-clockwise, return to start, then execute two faster memory-replay laps. It handles vision loss, false positives, oblique views, range-sensor failures, and missed gate credits through dedicated fallback logic at every layer.

The project built practical depth across the robotics stack — OpenCV perception, geometric coordinate-frame projection, temporal filtering, finite-state machine design, trajectory replay planning, and PID cascade tuning — under real uncertainty from a randomized environment and a hard time budget.
